## Ringkasan Eksekutif

**Kondisi inti sistem: SEHAT.** Pembukuan double-entry seimbang, sub-ledger (AR/AP/deposit) konsisten, stok denormalisasi konsisten, tidak ada stok minus saat ini, tidak ada saldo akun yang drift. Health-check internal sistem hanya menandai 1 selisih stok sebesar 0,006 kg (rounding, dapat diabaikan).

**Namun ditemukan 7 bug LATEN** di logika kode — artinya **belum merusak data produksi saat ini**, tapi akan menyebabkan korupsi data/finansial bila skenario pemicunya terjadi. Diverifikasi terhadap DB: HPP negatif = 0 kejadian, output produksi bercost-0 = 0, STT cancelled = 0, batch cancelled-yet-consumed = 0, ekor floating-point di saldo = 0.

## B. Bug Logika Kode (LATEN — belum merusak data)

### C1 — CRITICAL: GR/STT cancel tanpa guard stok minus + WAC dibiarkan stale
**File:** `server/src/services/goodsReceiptCancel.ts:62-88`

`cancelGoodsReceiptInTx` membalik movement masuk (`In`) dengan **decrement tanpa syarat**, tanpa cek stok cukup:
```ts
await tx.inventoryItem.update({ where: { id: grItem.inventoryItemId },
  data: { currentStock: { decrement: qty }, updatedAt: new Date() } });
await adjustWarehouseStock(tx, grItem.inventoryItemId, grItem.warehouseId, -qty);
```
Dua masalah:
1. **Tidak ada guard negative-stock.** Bandingkan dengan `productionRunCancel.ts:52-68` dan `movements.ts:509-511` yang mengecek `currentStock < qty` sebelum reverse In. GR cancel tidak punya. Block yang ada hanya: sudah-cancelled, legacy-backfill, dan PI-link-paid/submitted — tidak ada yang menutup kasus "barang sudah keluar".
2. **WAC tidak di-recompute** (komentar baris 72-73: "accept minor drift"). Padahal `goodsReceiptSubmit.ts:154-167` menaikkan WAC via `calcWeightedAverage` saat terima. Cancel meninggalkan WAC ter-inflasi.

**Skenario reproduksi:**
1. Item X: stok 0, WAC 0.
2. Submit STT terima 100 @ Rp10.000 → stok 100, WAC 10.000.
3. Jual/kirim 100 (DO + invoice) → stok 0.
4. Cancel STT → tidak ada guard → currentStock 0 − 100 = **−100** (item & per-gudang).
5. WAC tetap 10.000 (stale).

**Dampak:** Persediaan fisik negatif (korupsi data); saat inbound berikutnya, `calcWeightedAverage` masuk cabang `cQty.lte(0)` (weightedAverage.ts:32) → WAC di-anchor ke cost baru, nilai saldo −100 dibuang → COGS penjualan berikutnya salah (korupsi finansial).

**Status produksi:** 125 STT semua "Submitted", **0 cancelled** → belum pernah ter-trigger.

**Rekomendasi:** Tambah guard negative-stock (dengan opsi Admin override, mirip `productionRunCancel.ts:52-68`) sebelum decrement; pertimbangkan recompute WAC via pola `recalculateAccountBalances`.

### C2 — CRITICAL/HIGH: Cancel inbound batch yang sudah dikonsumsi tidak diblokir
**File:** `goodsReceiptCancel.ts:62-88`, `productionRunCancel.ts:46-82`, `invoiceCancellation.ts:196-214`, `deliveryOrderEdit.ts:55-69`

Ketersediaan batch dihitung dinamis di `routes/inventory/items.ts:123-137` sebagai `SUM(outbound movements WHERE sourceMovementId = batch.id AND isCancelled=false)`. Input produksi men-set `sourceMovementId` ke batch inbound yang dikonsumsi (`productionRunSubmit.ts:267`).

**Tidak ada satu pun** service cancel/edit yang mengecek consumer hilir (`sourceMovementId`) dari inbound yang dibatalkan.

**Skenario:**
1. Terima batch B (movement `m1`) 100 unit.
2. Produksi konsumsi 60 dari `m1` (input `sourceMovementId=m1`), output dijual.
3. Cancel STT yang membuat `m1` → `m1` di-set isCancelled, stok decrement 100, tapi `m1` masih dirujuk input produksi sebagai sumber batch.

**Dampak:** Referensi batch orphan; ledger ketersediaan batch (`items.ts`) menjumlah konsumsi terhadap inbound yang sudah void; jejak audit cost (`batchUnitCost`) menunjuk sumber yang dibatalkan. Kombinasi dengan C1 = jalur konkret ke stok negatif.

Untuk production cancel/movements cancel, guard item-level **memitigasi sebagian** (tak bisa reverse In di bawah total stok), tapi **tidak mendeteksi konsumsi batch-level** bila total stok masih cukup dari batch lain → consumer tetap bisa menunjuk `sourceMovement` yang dibatalkan. (Severity kasus ini HIGH.)

**Status produksi:** 0 batch cancelled-yet-consumed → belum terjadi.

**Rekomendasi:** Sebelum cancel inbound, cek `stockMovement WHERE sourceMovementId=<itu> AND isCancelled=false` dan blokir (atau cascade). Tambah ke GR cancel, production cancel, movements cancel.

### H1 — HIGH: HPP produksi bisa NEGATIF saat NRV by-product > biaya total
**File:** `server/src/services/productionRunSubmit.ts:321-327`
```ts
const numerator = totalMaterialCost.plus(totalCostInputSide)
  .plus(totalCostOutputSide).minus(totalByproductValue);
computedHpp = numerator.div(totalMainOutputQtyDec).toDecimalPlaces(4);
```
Tidak ada guard `numerator >= 0`.

**Skenario angka:** input 1.000 kg @ Rp1.000 = Rp1.000.000; by-product 200 kg NRV Rp6.000 = Rp1.200.000; main output 800 kg → numerator = 1.000.000 − 1.200.000 = −200.000 → HPP = −250/kg.

**Dampak:** main output dapat `unitCost` negatif → di baris 341 `unitCost > 0` false (averageCost tak ter-update, diam-diam diabaikan); di baris 436-437 `val ≤ 0 continue` → output tidak di-DR sama sekali, input full di-CR → seluruh selisih dibuang ke HPP Beras (5.1). Stok output naik qty tanpa nilai → GL vs stok divergen. `computedHpp`/`unitCostLoaded` negatif tersimpan → margin report salah.

**Status produksi:** `computed_hpp < 0` = **0 baris** → belum terjadi.

**Rekomendasi:** Clamp HPP ≥ 0, atau tolak/peringatkan run saat NRV by-product > biaya.

### H2 — HIGH: Line produksi bercost-0 di-skip dari GL → stok bertambah/berkurang tanpa GL
**File:** `productionRunSubmit.ts:417` (input) & `:437` (output) — `if (val <= 0) continue;`

Line dengan `val ≤ 0` di-skip dari journal, tapi stock movement & currentStock tetap dibuat di loop sebelumnya (247-275 / 335-383). Stok berubah **tanpa** padanan GL untuk line itu.

**Skenario:** output main dengan computedHpp = 0 (semua biaya 0, material 0 karena batch cost 0), atau input dengan averageCost 0 (item belum pernah berharga) → stok masuk/keluar tanpa DR/CR.

**Dampak:** Persediaan (kuantitas) naik/turun tanpa nilai GL → neraca vs nilai stok fisik divergen.

**Status produksi:** output produksi `unit_cost=0` = **0 baris** → belum terjadi (semua item produksi sudah berharga).

**Rekomendasi:** Pastikan setiap perubahan stok punya padanan GL, atau tolak line bercost-0 dengan peringatan.

### H3 — HIGH: Edit stock-movement tidak recompute WAC pada In baru
**File:** `server/src/routes/inventory/movements.ts:295-489` (PUT `/:id`), khususnya 367-371

Saat edit, movement lama di-reverse & movement baru di-apply, tapi WAC **tidak pernah** di-update untuk In baru (hanya `currentStock: { increment }`). POST handler (118-121) meng-update WAC; PUT tidak.

**Skenario:** Buat In 100 @ Rp5.000 → WAC 5.000. Edit jadi 100 @ Rp50.000. Stok net benar, tapi WAC tetap 5.000 — perubahan cost hilang diam-diam.

**Dampak:** WAC drift / nilai persediaan & COGS understate, tanpa peringatan. (Tool Admin/Accountant.)

**Catatan tambahan (LOW):** baris 372-373 reversal & re-apply pakai `oldMov.warehouseId`; bila `body.warehouseId` berubah, perpindahan gudang diabaikan.

**Rekomendasi:** Recompute `averageCost` di PUT untuk In baru (dan back-out kontribusi In lama), seperti POST.

### M1 — MEDIUM: Landed cost realign ke stok TERKINI, bukan stok saat barang masuk
**File:** `server/src/services/purchaseInvoiceSubmit.ts:451-465`
```ts
const newAvg = stock.times(oldAvg).plus(adj.delta).div(stock)...
```
`delta` (penyesuaian landed cost) dibagi ke `currentStock` terkini. Jika sebagian stok STT sudah keluar sebelum PI submit, delta penuh diserap ke sisa stok → averageCost sisa overstate, dan COGS barang yang sudah keluar tidak ikut dikoreksi.

**Skenario:** STT 1.000 kg provisional Rp5.000; 600 kg terjual; PI datang landed cost +Rp500.000. newAvg = (400×5.000 + 500.000)/400 = Rp6.250 (seharusnya ~Rp5.500). 400 kg sisa overstate Rp300.000; COGS 600 kg understate Rp300.000.

**Status produksi:** jeda STT→PI semua **≤3 hari** → window sempit, risiko rendah di praktik. Ada 12 PI dengan biaya tambahan/potongan (area aktif).

**Rekomendasi:** Alokasikan delta ke qty saat penerimaan (kuantitas STT asli), bukan stok terkini; koreksi COGS yang sudah ter-posting jika barang sudah keluar.

### M2 — MEDIUM: DO cancel revert deliveredQty walau reversal stok di-skip
**File:** `server/src/services/deliveryOrderCancel.ts:42-93`

Bila `stockMovement` line hilang/sudah-cancelled, reversal stok di-skip (43-49, benar — hindari double-reverse). **Tapi** loop decrement `salesOrderItem.deliveredQty` (68-93) jalan tanpa syarat untuk tiap line ber-`salesOrderItemId`.

**Skenario:** Line yang movement-nya sudah dibatalkan terpisah (via `movements PUT /:id/cancel`) → saat DO cancel, stok TIDAK di-increment (skip), tapi deliveredQty TETAP dikurangi → deliveredQty SO divergen dari stok riil.

**Dampak:** Status fulfillment SO drift dari realita (kasus tidak umum).

**Rekomendasi:** Decrement deliveredQty hanya bila reversal stok line itu benar-benar dijalankan.

## D. Catatan Penyajian Akuntansi (bukan bug, perlu konfirmasi)

- **AKU-1:** Saat output produksi > nilai input (`diff > 0`), selisih di-CR ke HPP/COGS 5.1 (`productionRunSubmit.ts:454-472`). JE tetap balance, tapi meng-kredit akun beban menghasilkan saldo COGS berkurang/negatif yang men-distorsi laporan HPP periodik. Idealnya "gain on conversion" ke akun varian produksi tersendiri. **Konfirmasi dengan akuntan.**

## E. Bug Konsistensi (Severity rendah, sudah ada di data)

- **CON-1 (LOW/konsistensi):** `movements.ts:108-109` & `:377` — satu-satunya jalur posting GL yang pakai `Number` arithmetic (`qty * unitCost`), bukan Decimal. Terbukti empiris menghasilkan ekor float (`0.1 × 8333.33 = 833.3330000000001`). Karena DR==CR pakai nilai sama, JE tetap balance & **belum mencemari saldo** (verifikasi: 0 ekor float di ALE). Tetap inkonsisten dengan ~6 jalur lain yang pakai `Decimal(...).toDecimalPlaces(2)`. **Rekomendasi:** bungkus dengan Decimal.

- **CON-2 (LOW, data lama):** Snapshot stok per tanggal lampau menampilkan qty negatif untuk item dengan opening-balance yang ditulis langsung ke `inventory_stocks` tanpa StockMovement (3 item per 2026-05-01). Ini **keterbatasan yang sudah dideklarasikan** di `stockSnapshot.ts` (anchor-walk-back), bukan bug baru. Snapshot hari ini tetap 100% cocok dengan stok live.

## F. Yang Terverifikasi AMAN (tidak perlu tindakan)

- WAC formula: guard `cQty≤0` & `totalQty≤0` lengkap, anchor ke inUnitCost, tanpa div-by-zero (`weightedAverage.ts:32-44`).
- OEE: clamp 0-1, semua pembagi di-guard (`oee.ts`).
- Rendemen/yield: div-by-zero ter-guard (`input>0 ? ... : null`).
- COGS penjualan: pakai cost terkunci di DO (bukan WAC terkini), konsisten dengan stok yang dikurangi, arah DR/CR benar.
- Landed cost allocation: pola "last item absorbs remainder" → balance persis, div-by-zero ter-guard.
- accountBalance: arah normal-balance benar, ada rebuild dari sumber kebenaran (anti-drift).
- COGS backfill: guard div-by-zero & clamp ≥0.
- Cancel/edit: JE+ALE+balance ter-reverse konsisten; idempotency ter-guard via status (tak bisa double-reverse); update stok dual (item + per-gudang) di semua path kecuali isu guard C1.
- Validasi Zod runtime: qty negatif/rate negatif/NaN/array kosong semua ditolak 400 dengan pesan jelas.
- RBAC runtime: Viewer→mutasi 403, StaffProduksi→bypass-minus 403, no-auth→401, CSRF→403.

## Kesimpulan

Tujuh bug logika yang ditemukan bersifat **laten** — perlu diperbaiki sebelum skenario pemicunya muncul (terutama **C1** karena cancel STT adalah operasi normal yang belum pernah dipakai, dan **H1/H2** pada produksi dengan by-product bernilai tinggi atau item baru bercost-0).
